## RM-correlated nv_alloc_pages timeline

First kernel RM error:

`RM mono = 124729.577845`

`NVRM: ... NV_ERR_NO_MEMORY (0x00000051) returned from
_memdescAllocInternal(pMemDesc) @ mem_desc.c:1359`

All relevant calls below are from `VLLM::Worker-1679397`, use
`contiguous=0`, and are measured on the same monotonic trace clock.

1. An outer `nv_alloc_pages` call begins at `124729.484145`, 93.700 ms before
   the RM log, with `page_count=819200`, `page_size=65536`. The public API
   arguments represent 50.0 GiB (`819200 * 65536`). It returns `NV_OK` at
   `124729.765293`, 187.448 ms after the RM log, after about 281.148 ms total.
   Therefore the kernel RM error occurs while this outer call is in flight,
   but the outer call eventually succeeds.

2. A later outer call begins at `124729.802505`, 224.660 ms after the RM log,
   with `page_count=409600`, `page_size=65536` (25.0 GiB by the public API
   arguments). It returns `NV_ERR_NO_MEMORY (0x51)` at `124729.891936`,
   314.091 ms after the RM log, after about 89.431 ms.

3. Only about 0.322 ms after that failed return, another call on the same
   worker begins at `124729.892258` with the same `page_count=409600` but
   `page_size=4096`. It therefore represents 1.5625 GiB, not 25 GiB, and
   returns `NV_OK` at `124730.004350` after about 112.092 ms.

Do **not** claim that the kernel `_memdescAllocInternal` log and the later
25 GiB outer `nv_alloc_pages_ret=0x51` are necessarily one call. Their timing
rules out a simple one-to-one interpretation: the later outer call starts more
than 224 ms after the kernel log. The kernel failure is instead compatible
with an internal/nested allocation or recoverable internal failure while the
preceding 50 GiB outer call is in flight, followed by a distinct outer
25 GiB/64 KiB-page failure.

Likewise, do not call the immediately following 4 KiB-page call an equivalent
retry: although the page count is identical, the public API request size is
1/16 as large. It is suggestive of a fallback/recovery sequence, but deeper RM
source or narrower tracing is required to establish that relationship.

## Exact NVIDIA 580.178.04 source implication

In the exact open kernel source for driver 580.178.04, `nv_alloc_pages()` takes
`page_count`, `page_size`, and `contiguous` directly. For non-contiguous calls,
it rejects `page_size == 0`, sets `at->order = get_order(page_size)`, and calls
`nv_alloc_system_pages(nv, at)`.

R8's failing calls all have `contiguous=0`. Therefore the next driver boundary
of interest is `nv_alloc_system_pages`, not `nv_alloc_contig_pages` and not the
PMA/DMA/PMM paths that remained silent in R8.

The exact Linux allocation order corresponding to `page_size=65536` must not
be inferred until the live host base `PAGE_SIZE` is recorded; this is an
ARM64 system and the base page size should be verified rather than assumed.

## Tooling defect found during R8

The isolated safety monitor in the R8 child exited immediately with:

`ERROR: unknown argument: --swap-activity-gate-mib`

The current canonical `scripts/runtime/monitor-runtime.sh` no longer accepts
that historical option. The preserved `/tmp/run-h6-kv16-trace-r7.sh` used to
derive R8 is therefore stale relative to the current monitor CLI. This does
not invalidate the R8 model/outer-kernel classification, but the R8 run has no
valid isolated-monitor protection evidence.

Before another model run, the child derivation must remove the obsolete
argument (or be rebuilt from a current canonical control path), and the next
runner must verify monitor CLI compatibility during preflight.
