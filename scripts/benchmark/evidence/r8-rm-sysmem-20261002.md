## Correct nv_alloc_pages / nv_alloc_system_pages semantics

The exact NVIDIA 580.178.04 open-kernel source changes an important initial
interpretation of the probe arguments.

`nv_alloc_pages()` takes `page_count`, `page_size`, and `contiguous` directly.
For a non-contiguous request it sets:

`at->order = get_order(page_size)`

and then calls:

`nv_alloc_system_pages(nv, at)`.

Inside `nv_alloc_system_pages()` the total system-memory byte count is based on
`at->num_pages * PAGE_SIZE`, where `at->num_pages` is the probed `page_count`.
The requested `page_size` instead controls the Linux allocation order/chunk
size through `get_order(page_size)`.

Therefore **`page_count * page_size` must not be used as the total request
size**. The earlier provisional 50 GiB / 25 GiB labels were incorrect and are
superseded by this source-grounded interpretation.

On the live DGX host, the repository analyzer now obtains the base page size
with `os.sysconf("SC_PAGE_SIZE")`. Once that value is printed, it calculates:

- total request bytes = `page_count * host PAGE_SIZE`;
- allocation order = the `get_order(page_size)` equivalent;
- allocation chunk bytes = `host PAGE_SIZE << order`;
- number of allocation chunks required to cover the request.

This is especially important for the two adjacent `page_count=409600` calls:
they have the **same total byte count on the same host**, while changing only
the requested allocation granularity from `page_size=65536` to
`page_size=4096`. If the live base page size is 4096, this is specifically an
order-4 to order-0 fallback for the same total 1.5625 GiB system-memory
request. Do not state that order interpretation until the analyzer records the
live base page size.

## RM-correlated nv_alloc_pages timeline

First kernel RM error:

`RM mono = 124729.577845`

`NVRM: ... NV_ERR_NO_MEMORY (0x00000051) returned from
_memdescAllocInternal(pMemDesc) @ mem_desc.c:1359`

All relevant calls below are from `VLLM::Worker-1679397`, use
`contiguous=0`, and are measured on the same monotonic trace clock.

1. An outer `nv_alloc_pages` call begins at `124729.484145`, 93.700 ms before
   the RM log, with `page_count=819200`, `page_size=65536`. It returns `NV_OK`
   at `124729.765293`, 187.448 ms after the RM log, after about 281.148 ms.
   Therefore the kernel RM error occurs while this outer call is in flight,
   but the outer call eventually succeeds.

2. A later outer call begins at `124729.802505`, 224.660 ms after the RM log,
   with `page_count=409600`, `page_size=65536`. It returns
   `NV_ERR_NO_MEMORY (0x51)` at `124729.891936`, 314.091 ms after the RM log,
   after about 89.431 ms.

3. Only about 0.322 ms after that failed return, another call on the same
   worker begins at `124729.892258` with the **same `page_count=409600`** but
   `page_size=4096`. It returns `NV_OK` at `124730.004350` after about
   112.092 ms.

Because total non-contiguous sysmem request bytes are based on
`page_count * PAGE_SIZE`, calls 2 and 3 are now strong evidence of a same-size
request being retried/fallen back with a smaller allocation granularity. This
is materially stronger than the earlier provisional interpretation. The exact
order change still depends on the live host base `PAGE_SIZE`, which the deep
analyzer records explicitly.

Do **not** claim that the kernel `_memdescAllocInternal` log and the later
outer `nv_alloc_pages_ret=0x51` are necessarily one call. Their timing rules
out a simple one-to-one interpretation: the later outer call starts more than
224 ms after the kernel log. The kernel failure is compatible with an internal
or nested allocation failure, or a recoverable RM failure, while the preceding
`page_count=819200` outer call is in flight. That outer call eventually returns
`NV_OK`.

## Next driver boundary

R8's RM-correlated calls all have `contiguous=0`, and the exact 580.178.04
source dispatches those calls to `nv_alloc_system_pages()`.

Therefore the next driver boundary of interest is `nv_alloc_system_pages`, not
`nv_alloc_contig_pages` and not the PMA/DMA/PMM paths that remained silent in
R8.

A future R9, if still needed after preserved-trace analysis, should narrow the
driver probes around `nv_alloc_pages` + `nv_alloc_system_pages` and retain the
same low-volume Linux allocator trace.

## Tooling defect found during R8

`ERROR: unknown argument: --swap-activity-gate-mib`

The current monitor implementation no longer accepts that historical option.
The preserved `/tmp/run-h6-kv16-trace-r7.sh` used to derive R8 is therefore
stale relative to the current monitor CLI. This does not invalidate the R8
model/outer-kernel classification, but the R8 run has no valid isolated-monitor
protection evidence.

Before another model run, the child derivation must remove the obsolete
argument (or be rebuilt from a current canonical control path), and the next
runner must verify monitor CLI compatibility during preflight.
