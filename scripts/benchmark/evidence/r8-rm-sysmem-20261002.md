## Source-grounded allocation semantics

The exact NVIDIA 580.178.04 open-kernel source is required to interpret the
probe arguments correctly.

`nv_alloc_pages()` takes `page_count`, `page_size`, and `contiguous`. For a
non-contiguous request it sets:

`at->order = get_order(page_size)`

and calls:

`nv_alloc_system_pages(nv, at)`.

Inside `nv_alloc_system_pages()` the total system-memory request is based on
`at->num_pages * PAGE_SIZE`; `at->num_pages` is the probed `page_count`.
`page_size` instead controls the Linux allocation order/chunk size.

The live DGX host reports:

`PAGE_SIZE = 4096`

Therefore the relevant 64 KiB requests are **order 4**, and a 4 KiB request is
**order 0**. Do not use `page_count * requested_page_size` as total bytes.

## Normalized failed-vs-preceding-success comparison

The failed 1.5625 GiB order-4 call is shorter than the preceding successful
3.125 GiB order-4 call, so raw counts alone are misleading. Per-millisecond
rates show:

| Metric | 3.125 GiB order-4 success | 1.5625 GiB order-4 failure | Failure / success |
|---|---:|---:|---:|
| compaction try / ms | 3.205 | 2.807 | 0.88x |
| direct reclaim / ms | 0.096 | 0.816 | **8.50x** |
| extfrag / ms | 97.418 | 42.994 | 0.44x |
| ownership-changing extfrag / ms | 6.008 | 9.024 | 1.50x |
| ownership / extfrag | 6.17% | **20.99%** | **3.40x** |
| fallback-gap>=2 / extfrag | 27.36% | **39.61%** | 1.45x |

The important distinction is therefore not simply "more compaction" or "more
extfrag". The successful call actually has more of both in absolute terms and
higher rates for total extfrag. The failed call instead shows much stronger
**direct reclaim intensity** and a much larger fraction of extfrag events that
change pageblock ownership / require larger fallback distance.

Linux's `mm_page_alloc_extfrag` tracepoint is explicitly intended to expose
external fragmentation affecting high-order allocation success. This supports
interpreting the order-4 failure as a high-order allocation-state problem, but
it still does **not** prove external fragmentation is the unique root cause.
The exact failing chunk/iteration inside `nv_alloc_system_pages()` was not
captured in R8.

## Strongest current mechanism

The strongest mechanism supported by R8 is now:

1. late initialization places RM/Linux sysmem allocation under substantial
   order-4 pressure;
2. an RM `_memdescAllocInternal` `NV_ERR_NO_MEMORY` occurs while an earlier
   3.125 GiB order-4 outer allocation is in flight, but that outer allocation
   eventually succeeds;
3. a later 1.5625 GiB order-4 `nv_alloc_pages` call returns `0x51` directly;
4. the failed interval has a sharply higher direct-reclaim rate and a higher
   ownership-changing/far-fallback fraction than the preceding successful
   order-4 call;
5. `0.322 ms` later, the same 1.5625 GiB total request succeeds as order 0 with
   no compaction/extfrag activity.

This is much narrower than the previous generic "RM/UVM/Linux allocator timing
collision" hypothesis. It identifies a recoverable **RM sysmem high-order
allocation failure followed by lower-granularity fallback** as the observed
failure mechanism.

Do not yet promote this to "external fragmentation is the root cause". R5/R6
and the first R8 call prove that strong compaction/extfrag can coexist with
success, and R8 did not record the exact iteration inside
`nv_alloc_system_pages()` that failed.

## First RM log vs outer `nv_alloc_pages_ret=0x51`

Do not claim that the kernel `_memdescAllocInternal` log and the later outer
`nv_alloc_pages_ret=0x51` are the same single call. The failed outer call starts
`224.660 ms` after the first kernel log. The earlier 3.125 GiB outer call spans
the first kernel log and still returns `NV_OK`.

The first RM error is therefore compatible with an internal/nested or
recoverable RM allocation failure during the earlier outer request. The later
outer order-4 failure is a distinct directly observed sysmem failure.
